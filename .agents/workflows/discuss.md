# Discuss 知識點驗證工作流程

本工作流程是進入實作階段 (`/proceed`) 前的關鍵知識檢驗環節。根據 `issues/<topic-folder>/TASKS.md` 所列任務，逐題檢驗開發者是否掌握實作所需的核心概念與官方權威文獻，並將經過驗證的知識連結收錄至 `KEEP.md`。

## 執行步驟 (Workflow Steps)

### 步驟 1：前置產出物檢查 (Prerequisite Gate)
在展開知識點討論前，必須確認前續階段檔案皆已到位：
1. **檢查主題資料夾**：確認專案根目錄下目標 `issues/<topic-folder>/` 是否存在。
2. **檢查核心三產出物**：
   - `issues/<topic-folder>/REQUIREMENT.md`
   - `issues/<topic-folder>/PLAN.md`
   - `issues/<topic-folder>/TASKS.md`
3. **未通過門檻之處置（強制中斷）**：
   - 若缺少上述任一檔案，**拒絕執行**。
   - 缺少需求時引導執行 `/grill-me`；缺少計畫或任務時引導執行 `/plan`。

### 步驟 2：剖析任務知識點與單題出題
1. **分析 TASKS.md 核心知識點**：
   - 深入檢視 `TASKS.md` 中尚未實作的任務。
   - 提煉出實作各任務所必須掌握的關鍵技術、官方文件章節、通訊協定、核心演算法、指令用法或參數配置。
2. **單一聚焦出題（一次只問一題）**：
   - 一次只提出一個知識點問題，明確指出該問題對應於 `TASKS.md` 的哪個任務或技術關鍵點。
   - 題目範例：「在實作任務 2 的 JWT 驗證與過期輪替時，所使用的函式庫其官方推薦的最佳實踐與安全性配置為何？請提供重點說明與參考 URL。」

### 步驟 3：嚴格驗證開發者回答與 URL
當開發者作答時，執行嚴格的雙重驗證：
1. **口頭概念說明檢查**：
   - 開發者**必須提供具體的口頭概念說明**。
   - **若僅提供 URL 而未附口頭說明，或說明過於空泛/錯誤，一律判定為「不通過」**，要求開發者補充其理解，以確保開發者真正具備該核心概念。
2. **URL 內容實質驗證**：
   - 檢查開發者提供的參考 URL 是否有效且精確對應問題答案（必要時使用工具抓取網頁內容驗證）。
3. **驗證不通過時**：
   - 點出說明與官方文獻中的盲點或差異，請開發者重新調整說明或提供正確連結，直到本題過關前**切勿**跳到下一題。

### 步驟 4：合格寫入 KEEP.md
當開發者的口頭說明正確且 URL 經查證無誤時：
1. **存檔至 `KEEP.md`**：
   - 將該知識點寫入專案根目錄的 `KEEP.md`（若檔案不存在則自動建立）。
2. **嚴格格式規範**：
   - **不需要任何標題、不需要多層結構**，一律使用單層 Markdown 清單追加記錄：
     ```markdown
     - [知識點簡述](URL)
     ```
   - 自動去重，若該 URL 已存在則不重複寫入。
   - 禁止擅自修改貼上的 URL，包含開發者註明的 `:~:text=` 錨點。
3. **推進下一題**：
   - 提示本題已通過並記錄，接著提出下一個任務的知識點問題。
   - 循環進行，直到所有任務核心知識點皆驗證完畢，或開發者主動表示「結束」為止。

### 步驟 5：雙向互動與反問規則
- 討論過程中，若開發者向 Agent 反問技術問題或請教最佳實踐：
  - Agent 回答時**必須附上對應的官方文件或權威文獻 URL**，嚴禁無來源的憑空推論。
  - 經雙方確認為實作關鍵知識點者，亦可同步按規範收錄至 `KEEP.md`。

### 步驟 6：完成驗證後的下一步 (Handoff)
- 當開發者表示結束或知識點已齊全時，向開發者彙整 `KEEP.md` 已收錄的清單。
- 提示開發者知識點門檻已達成，可直接執行 `/proceed` 開始逐項實作代碼。
